# 资料检索修复（2026-11-08）

## 问题与证据

用户在 Windows 中询问小麦麦穗局部发白和疑似赤霉病的权威资料，网页返回“搜索服务暂时不可用”，此前本地知识查询也曾被报告失败。

检查发现以下可复现问题，而非证明公开网上没有资料：

1. `web_search.py` 的官方来源配置使用 `Path.read_text()`，没有明确编码。当前含中文 UTF-8 配置按 GBK 解码会报 `UnicodeDecodeError`。该读取位于原网页请求 try 块外，导致补充检索中止并被工具层汇总为失败。用 GBK 默认编码替身已复现并覆盖回归。
2. 本地知识库校验原文的 SHA-256。Windows Git 可能把 LF 转为 CRLF，即使内容没变也会导致资料校验失败。修复仅容忍精确的 CRLF→LF 换行转换；其他内容改动及不可追溯引文仍被拒绝，并用 `.gitattributes` 固定后续原文检出的字节。
3. 原搜索只使用单个 Bing RSS 入口，公开接口的中文结果可能无关或为空。原补充检索遇到重定向会跳过网页；配置、网络、格式与无匹配结果也缺少区分。

用户本机实际错误类型仍需以更新后的结果判断。云端可访问不能证明用户电脑具有相同代理、编码或网络条件。

## 修改后的行为

- 搜索及官方情报配置显式使用 UTF-8（兼容 BOM）；配置缺失或损坏返回安全原因，不使全部搜索中断。
- 先查公开搜索，再实时读取既有官方来源页，仍无结果时尝试国内 Bing 入口，整个流程有时间和响应大小限制。
- 只跟随有限次受支持的搜索域名/官方域名跳转，不跳转到私网或任意地址。保留 TLS 验证和系统代理设置。
- 过长自然语言搜索请求提取已有的农业关键词；不凭空补出病名。保留 `site:` 限制，相关性同时检查小麦和已明确的病害关键词。
- 标题、URL、发布日期来自真实响应；官方补充资料带获取时间，并明确标注历史文章和适用边界。仍然只补充已有两篇官方来源，不能宣称全网覆盖。
- 区分超时、代理、证书、HTTP 错误、配置读取失败和无匹配结果，返回正文与网页卡片保留具体原因；不暴露密钥、代理地址或原始异常消息。
- 搜索失败仍正常收尾，不编造网页或用药结论。既有案例不因搜索失败而删除。

- 发布日期：2026-04-20
- https://www.moa.gov.cn/xw/zwdt/202604/t20260420_6483403.htm

本地知识库返回 1 条相关观察资料。公开文章是历史资料，不是当前郑州预警，也不是模拟照片病因的确诊证据。

可复核的安全输出：`docs/research/search-connectivity-2026-11-08.json`。

277 项后端自动化测试、6 项相关浏览器测试通过。新增测试覆盖 GBK 默认编码、CRLF 原文、修改内容仍被拒绝、来源配置缺失后的备用入口、站点/病害过滤、安全跳转、长度/时间预算、具体网络原因及来源卡片刷新保留。自动化网络场景使用替身；上述真实公开网页访问单独记录。

## Windows 更新和自检

1. 拉取最新代码，关闭旧后端，再运行 `start.bat`。
2. `/api/agent/capabilities` 中 `server_version` 应为 `2026.11.08.search`。
3. 保留当前 DeepSeek 文字＋讯飞图片配置，在原对话重新发送搜索请求；旧消息不会被自动改写成新结果。
4. 若仍无结果，双击 `check_search.bat`。脚本使用项目虚拟环境，检查本地知识库和固定公开关键词，报告检索阶段与真实 URL；无需新增 Key、不调用模型、不读取私人案例、不改代理。
5. 提供自检输出即可。若明确提示代理/证书/网络故障，再按实际原因修正本机环境，不能把云端成功当作本机已修复。
